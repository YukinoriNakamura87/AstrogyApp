## 1. 設計方針
 
個人利用を起点としつつ、将来的なサービス化の可能性も見据えた構成とする。そのため、技術選定においては以下を重視した。
 
- 開発者（ゆき氏）の既存スキル（Vue.js、フルスタック経験、MySQL経験）を活用できること
- チャート計算における精度・信頼性（占星術ツールとして最も重要な要件）
- 将来の本番運用・拡張に耐えられる構成であること
- 開発環境の再現性（Docker）

## 3. 技術スタック
 
| レイヤー | 技術 | 採用理由 |
|----------|------|----------|
| 開発環境 | Docker Compose | 環境構築の再現性・チーム間（将来）での環境統一 |
| フロントエンド | Vue.js（Nuxt.js） | 開発者の既存スキルを活用。SSR・PWA対応も可能 |
| バックエンド | Python（FastAPI） | Kerykeion（Python専用ライブラリ）を利用するため必須 |
| チャート計算 | Kerykeion | Swiss Ephemerisベースの高精度計算。SVGチャート生成も標準搭載 |
| データベース | PostgreSQL | 構造化データに強く、JSON型もサポート。将来の商用運用にも対応できる実績 |
 
### 補足：データベース選定について
 
PostgreSQLは「Python向け」という直接的な理由で選んだものではない。FastAPI（Python）はPostgreSQL・MySQL・SQLiteなど主要なDBと問題なく接続できる。今回PostgreSQLを選んだ理由は、以下の3点による：
 
1. クライアント情報・チャートデータ・解釈辞書という明確な構造化データに向いている
2. アスペクト情報など可変構造のデータをJSON型で柔軟に扱える
3. 個人利用から将来の商用運用への移行を想定した場合の実績・信頼性
ゆき氏はMySQLの技術歴が長いが、実用上の大きな差はないことを確認の上、将来性を考慮してPostgreSQLを採用することで合意した。

## 5. データモデル（概要）
 
詳細なテーブル設計は実装フェーズで確定するが、企画書で定義したデータ構造をもとに以下の基本エンティティを想定する。
 
```
Client（クライアント）
├── 基本情報（氏名・生年月日・出生時刻・出生地 等）
│
├── Chart（チャートデータ）※クライアントに対して1つ
│   ├── 天体・ハウス・アスペクトの計算結果
│   └── ChartInterpretationMemo（チャート解釈メモ）
│       └── 天体ごとの解釈（参照・上書き可能、永続データ）
│
└── Session（セッション記録）※クライアントに対して複数
    └── セッションごとの記録（日時・内容・気づき等）
 
DictionaryEntry（解釈辞書エントリー）
├── キー：天体×サイン / 天体×ハウス / アスペクト
├── 解釈テキスト
├── 作成日・更新日
└── 参照元セッション（紐付け）
```
 
### 設計上の重要なポイント
 
- **ChartInterpretationMemo**（チャート解釈メモ）と**Session**（セッション記録）は明確に分離されたエンティティとする
  - チャート解釈メモ：クライアントのチャートに対する解釈。1人のクライアントに対して天体ごとに1つ存在し、セッションを重ねるたびに参照・上書きされる
  - セッション記録：個々のセッションの記録。セッションごとに独立して蓄積される（上書きされない）
- **DictionaryEntry**（解釈辞書）は特定のクライアントに紐づかない、ゆき氏個人のナレッジベースとして独立させる
  - ChartInterpretationMemoから登録・参照される双方向の関連を持つ

## 6. API設計の方針（概要）
 
FastAPIによるRESTful API構成を想定。主要なリソースは以下の通り（詳細は実装フェーズで確定）。
 
| リソース | 主な操作 |
|----------|----------|
| `/clients` | クライアントのCRUD |
| `/clients/{id}/chart` | チャートデータの取得・計算（Kerykeion呼び出し） |
| `/clients/{id}/chart/memos` | チャート解釈メモの取得・更新 |
| `/clients/{id}/sessions` | セッション記録のCRUD |
| `/dictionary` | 解釈辞書エントリーのCRUD・検索 |
 
チャート計算（Kerykeion呼び出し）は計算コストが発生するため、初回計算後はDBにキャッシュし、再計算が不要な設計とする。

## 7. チャート計算（Kerykeion）について
 
| 項目 | 内容 |
|------|------|
| ライブラリ | Kerykeion（Python） |
| 計算エンジン | Swiss Ephemeris（業界標準・高精度） |
| 対応範囲 | ネイタル・トランジット・シナストリー・コンポジット |
| 出力 | 天体・ハウス・アスペクトの計算結果、SVGチャート画像 |
 
個人利用フェーズでは無料のOSSライブラリとして利用する。将来サービス化する際は、同エンジンをベースとしたホスト型APIへの移行パスも用意されているため、データ互換性を保ったまま拡張できる。

セッション画面（チャート表示＋メモ入力）が最も操作頻度が高いため、レスポンシブ設計においてはこの画面のUXを優先的に検証する。

## 11. 将来のサービス化を見据えた拡張性
 
現時点ではスコープ外だが、技術選定の段階で以下の拡張性を確保している。
 
- **PostgreSQL**：個人利用から商用利用までスケール可能
- **FastAPI**：APIとして外部公開・複数ユーザー対応への拡張が容易
- **Kerykeion → ホスト型APIへの移行パス**：同エンジンのためデータ互換性を維持できる
- **Docker構成**：本番環境への展開時も同様の構成を活用できる
